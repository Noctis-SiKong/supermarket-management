## 0. 总体评价

**优点**

1. 六条业务链都有明确服务承载（补货、报损/修正、退换、查询、冲销），端到端职责切分基本清楚。
2. 计算/校验与编排分离（`QuotaCalculator`、`QualityPairValidator`、`DependencyChecker`、`ReversalPlan`），便于纯逻辑单测。
3. 明确"不保存、统一经 `SubmissionPort`（IF-05）提交"的持久化边界，未越界 A 的 persistence/附件/根目录能力。
4. 外部依赖只面向接口，并标注 `IF-03/04/05/06/11`，符合分工清单的边界。
5. 主要路径上的组合/聚合、多重度、幂等键（`requestKey`/`eventKey`/`transferKey`）方向正确。

**总体判断**

V1 的结构方向可用，但存在 **8 项 P0（编码前必须处理）**：售后混合单能力、额度台账读取、换货替换品库存链路、库存流水关键字段、提交载体、权限/身份层、业务单据头/行归属、AC-87 凭证定位/追溯（依赖 A 的 IF-11 方案）。其余问题可作为 V2/技术设计收口，不阻塞 V1 冻结。

## 7. B 逐条决定（待 B 本人填写，报告 §3.4 使用）

> 说明：以下决定与理由必须由 B 本人作出；AI 不得代替。采纳/拒绝均需写理由，尤其"拒绝"要能说明为何不采纳。

| #    | 意见摘要                   | 决定（采纳/拒绝/修改后采纳） | 理由                                                                                                                    | V2 对应改动 |
| ---- | ---------------------- | --------------- | --------------------------------------------------------------------------------------------------------------------- | ------- |
| R-01 | 售后混合单能力                | 采纳              | `returnItems` 和 `exchange` 是两个独立方法，一次只能退或只能换。这与业务要求的可以退了又换不符，如果不调整，业务表单就会被拆分                                          |         |
| R-02 | 额度台账读取                 | 采纳              | QuoView为数据类，**`OriginalSaleReader.readLine(saleLineId)`**：只返回成交那一刻的快照，两者之间缺乏联系，即现在的系统缺乏算出剩余数量和剩余金额的能力，就会导致重复退款/超退     |         |
| R-03 | 换货替换品库存链路              | 修改后采纳           | 替换品必须先只从在售扣、不足再查看库存，此处要特别注意余量的变动                                                                                      |         |
| R-04 | 售后资格/期限策略              | 拒绝              | 现实情况中，售后逻辑一般由人工负责，没有在系统中的复杂逻辑实现                                                                                       |         |
| R-05 | 质量零差配对时序与字段            | 采纳              | 顾客买的东西有质量问题，换同款同数量，但这次换货仍然要占用原行的数量和金额额度，不修会导致重复退款和导致"不同商品、数量不同、有差额"的换货被当成特殊质量配对                                       |         |
| R-06 | 顾客交回损耗签名               | 采纳              | 顾客交回物和店内现货报损对库存影响截然不同，应当予以区分，不然会导致库存被误扣、库存混淆等问题                                                                       |         |
| R-07 | Redemption effect/kind | 采纳              | 一条核销明细要表达两个**互相独立**的维度，包括业务类型（退货、换货）和账务方向（占用还是释放），挤在一个kind字段里会导致分类的丢失                                                 |         |
| R-08 | Replacement 普通关联       | 采纳              | 业务背景中的审计要求从替换品能追到哪次核销、哪条原销售行。，不修会导致对不上帐（如原行 1 件实付 48，换现价 55 的新品，补 7；只能看到"换了 55 元的东西"，无法查看占用了哪 48 元额度）                 |         |
| R-09 | 冲销售后关联检查               | 采纳              | 若原销售 2 件，客户已退 1 件，店长直接整单作废会导致系统反向恢复 2 件库存、反向退 2 件款，但之前那笔退款还挂着从而使退款/核销/库存三重不一致。                                        |         |
| R-10 | 结清/尾差语义                | 采纳              | 本次提交正好结清该原行剩余数量时，最后一条应该用"剩余金额"兜底，不是再按公式算。不然会导致Q=3、P=10，分三次各退 1：每次都算 3.33，累计 9.99                                      |         |
| R-11 | 查询 scope 越权            | 采纳              | 一定要划分店员和管理员店长的权责                                                                                                      |         |
| R-12 | StockEntry 缺字段         | 采纳              | 缺失commit_ordinal、reverse_of_id、收货审核来源引用。不修会导致D1 依赖判断、整单冲销、恢复校验都没有数据承载。                                                |         |
| R-13 | 提交载体/基线                | 采纳              | `submit(changeSet)` 没有定义 changeSet；谁取 `baseLast`、失败怎么分类等问题都没有具体解决；不修就无法实现过期副本拒绝                                       |         |
| R-14 | 权限/身份层                 | 采纳              | 目前没有 AuthService/Session/Role，也没有 IF-01 依赖                                                                            |         |
| R-15 | 单据头/行归属                | 修改后采纳           | 补货/报损/售后/冲销都要业务单据，待A 确认 `common` 提供单据头/行类型                                                                            |         |
| R-16 | AC-87 凭证定位/追溯          | 修改后采纳           | 现状是`OriginalSaleReader.readLine(saleLineId)` 假设调用方已知原销售行 ID，缺失定位                                                      |         |
| R-17 | D1 输入与筛选               | 采纳              | D1 规定作废操作像剥洋葱一样从外往里做：销售 → 补货 → 收货；每冲销一层，下一层的依赖就少一条，直到原单可冲。如果某层永远清不掉，那张旧单就永远不能作废。                                      |         |
| R-18 | 冲销授权/审计                | 采纳              | 作废是高风险操作：只有店长/管理员可授权，必须留原因、授权人、时间。不修会导致店员也能作废，事后审计看不到"谁授权、何时、为何"。                                                     |         |
| R-19 | 错误模型统一                 | 采纳              | CUI 必须对非法输入/业务拒绝给出清楚反馈，不修CUI 只能笼统提示"操作失败"，或直接抛异常崩掉。                                                                   |         |
| R-20 | 文档级幂等键                 | 采纳              | IF-05 的幂等是整次业务请求级别：同一 `requestKey` 同内容重放 就返回既有结果，不重复入账；不修会导致用户双击"确认退货"，或网络超时后重试会生成两张售后单、两套核销等同于退两次钱                   |         |
| R-21 | 实体 ID 生成职责             | 修改后采纳           | 系统中的ID有两类，一类是实体ID、另一类是提交的序号；现有系统对此分配不清，应与A对齐                                                                          |         |
| R-22 | 输入校验落点                 | 采纳              | 非法输入应该在输入后的第一层就进行阻挡，拒绝非法数据入库                                                                                          |         |
| R-23 | 余额分位置展示                | 修改后采纳           | S（在售）/W（在仓）互斥、非负；核对信息要能分别显示，不能只给合计。但要有有关总余额的显示逻辑                                                                      |         |
| R-24 | Loss 字段补齐              | 采纳              | 字段缺失会导致业务逻辑无法跑通                                                                                                       |         |
| R-25 | MoneyEntry 归属          | 修改后采纳           | `MONEY_ENTRY` 是共享款项记录，在字段中只有 id/amountSigned/requestKey/reverseOfId，缺 document_id。应当在与A确认边界后作为**共享类型**由 `common`/A 提供 |         |
| R-26 | Replacement 快照字段       | 采纳              | 成交快照不可，不修会导致变换货后商品调价，历史记录只剩条码+金额，名称/单价丢失                                                                              |         |
| R-27 | 图面可读性                  | 拒绝              | 排版问题不影响代码实现                                                                                                           |         |
| R-28 | B 自有抽象不足               | 采用              | 缺失抽象类不符合要求建议抽取一个模板方法基类：`BusinessTransaction`，由补货/报损/售后/冲销继承                                                           |         |
| R-29 | 服务职责偏重                 | 修改后采纳           | 只抽 `EligibilityPolicy` 和 `AftersaleAssembler`，保留服务为编排者；在协调复杂性和维护复杂性中做折中                                               |         |
