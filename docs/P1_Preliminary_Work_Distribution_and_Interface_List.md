### 1.2 切分与状态口径

仅P1单店实体超市PC Java CUI；排除连锁、线上商城、称重、商品日期/批次/到期提醒/过期拦截，后者在P2也不预留。保留经办审计时间、促销起止及30日本地日历售后期限，它们不是商品日期功能。P2只保留Spec §14的GUI/Derby可替换边界说明，不设P2实现工作包。

六个功能包均从业务输入到持久结果及可查询证据闭环切分，包内负责该闭环的CUI交互、业务校验、保存接入与测试计划，不按实体、表、页面或技术层分人。每包/共享资产只有一位主责，主责独立完成自己的设计、实现和自测；另一成员在可交付版本形成后集中审计，问题交回主责修正。开始前仅共同确认必要输入输出、错误语义和统一保存边界，其他成员不共同修改内部实现。接口变化由提供方通知使用方，附版本差异、兼容影响及所需适配动作，最后统一联调/整体验收。跨包只使用共享能力契约，不直接改对方数据。售后退款/换货不得拆成两人各自维护额度；促销/销售也由一人主责，避免快照与分摊口径分裂。

本稿的负责人安排为预备方案；接口划分、DTO、错误码和方法签名属于**技术设计待主责交付后集中审计**，不要求负责人逐项审批普通技术细节，也不强制16项IF各建一个Java接口。不是新增FR/BR或已完成实现。IF/WP/SA/J/G/SYNC/T/Q编号仅为本稿索引。既有业务预期只引用Spec §17批准条目及§4–11规范；没有为登录、接口错误码或ID算法补造正式AC。

## 3. 接口清单

接口是双方如何协作的逻辑调用契约，独立于ERD的实体/外键。此处名称不是代码签名；参数载体、类型映射、错误码和调用形态均待V1/V2真实设计评审，不默认RPC、异步队列或额外服务。16项IF为逻辑职责，可合并实现为较少的类/接口；调用形式由双方设计评审后形成协作约定；不改变Spec批准状态。

业务包在一次业务确认中，先对同一工作副本校验、构建全部影响，再经IF-05一次提交；IF-07/13等内部协作不各自保存。查询/试算不等于确认成功。IF-05只能执行统一保存，不能替各业务包创造额外资格/审批规则。此边界来自Spec BR-07/17、§10.2、ERD-C07–09，具体工作副本调用形式为本稿工程建议。

### 4.2 工作副本生命周期（技术设计待主责交付后集中审计）

此处是实现单写者/原子语义的最小协作方案，不新增业务状态或额外持久化版本表。DTO和复制形式由交付后集中审计，无需用户逐项批准。

1. **创建者**：唯一运行时提交协调者（IF-05，A主责实现）从IF-04校验后的最新已提交快照创建本次隔离工作副本；记录读取的`baseLast=last_commit_ordinal`及相关单据version。schemaVersion只表示格式，不当运行提交版本。
2. **读取与可写权限**：业务入口持有只读基线，当前业务协调者独占本次副本；IF-07/12/13按调用次序形成变更，不把可写全局Map交给多个模块/线程同时覆盖。A/B是开发责任人，不是两名同时修改同一运行副本的写者。
3. **暂存与差异**：在当前副本内形成明确的单据、库存、核销、款项、附件引用及追溯关联差异；不把试算当成功、不提前保存某行/某模块。人工代码交接同样附文件版本/差异，不能直接覆盖对方未知修改。
4. **提交前复核**：在同一写锁下先查请求幂等，再比较baseLast/相关单据version与当前已提交基线；核对本次差异、权限、库存、双额度、审核防重及引用。若版本已变，拒绝旧副本覆盖，丢弃并用同一业务请求从最新状态重建/重算；不自动合并旧余额/旧核销金额。此为待交付后集中审计技术策略，不改业务金额公式。
5. **生效**：验证通过才分配本次候选last+1；计数/全部影响原子替换成功后发布新状态并返回成功。先前读取可能已陈旧，提交结果才是入账依据；成功请求重试优先回既有结果，不因baseLast旧而重复入账。
6. **失败/取消**：校验/组装/写入失败或确认前取消，只丢弃当前未提交副本，保留旧有效快照/last；临时文件不视为提交结果，附件孤立副本清理由主责交方案、使用方交付后集中审计。IF-11追溯写入与取消关联按§3.1候选方案评审：已生效/被引用记录不得按普通草稿直接删除；是否已有追溯提交必须先核对，不能笼统把全部售后草稿当作可丢弃或声称已有取消保留规则。若替换已成功不得把已提交数据当未成功丢弃，重启核对快照/请求键；完整恢复仍按D2，不能拼接版本。
7. **交接与证据**：每次问题记录请求键、baseLast、相关单据version、差异摘要、失败阶段和是否原子替换成功，不含明文密码/源用户路径。B评审旧副本覆盖及故障分支，A复核恢复；共享夹具只读版本一致，各自运行副本隔离。
