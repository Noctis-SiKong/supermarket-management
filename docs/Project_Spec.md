## 2 项目概述与边界

单家实体超市、PC端，用户为管理员、店长、店员。P1为轻量本地Java CUI，单机单进程、核心离线；构建依赖首次获取与业务离线运行分开验证。目标是把实际到货审核、在仓/在售转移、销售与原实付、促销、退换/损耗和追溯连接起来，同时满足课程需求/设计/HAI证据要求。

P1已定范围见FR-01–15：条码商品、收货待审/通过入仓、可选图片的CUI导入、两位置流水/期初、在售销售和收款确认、整单单活动择优、30天退换/部分退/数量核销/差额、记录权限、作废逆向联动、JSON文件恢复、补货和报损处置。商品日期及批次能力按U6全部撤销。

明确排除：连锁超市、线上商城、称重/小数数量、采购申请或订单事前审批、独立审核人/强制双人审核、日常退换逐笔等店长批准、第三个不可售库存桶、真实支付网关、依赖专用硬件的扫码、不做挂单。供应商采购退货未纳入，补正与退供不能混淆。保留未来扫码/硬件接入接口边界，不连接硬件或声称已实现；不为预留做P2实现。财务税务、薪资、积分等原未纳入功能仍不新增。

P1依课程使用Java、标准Maven或Gradle工程、Java集合与File I/O；本项目依用户选择Maven、JDK17、JUnit4.13.2、Jackson/UTF-8 JSON、BigDecimal及Asia/Shanghai。P2才实际实施Java GUI与Derby Embedded；相关硬要求留§14。商品过期销售拦截已由U6取消，不推断过期销售规则。

## 7 关键业务流程、数量与金额

### 7.1 收货、补货与位置影响

已选原方案A（U3 Q4），原方案B不再是当前选项。收货状态为待审核、审核通过、退回补充／修正；实收待审记录独立显示，不计两位置也不是第三库存桶。店长审核通过的业务一次入在仓，退回补正不入账，补正后通过只入一次。店长自审允许，管理员技术可审但原则由店长办理。附件由CUI本地路径导入，单次可跳过，缺图不自动拒审。审核补正不是供应商退货；后者不在P1流程内。

在售S=货架，在仓W=仓库，均非负整数，T=S+W；位置不等同启用/可销售状态。余额为已生效流水汇总，缓存可重建；期初必须有期初入库流水，不能无来源直接改余额。

| 动作 | 在售变化 | 在仓变化 | 流水/结果 |
|---|---:|---:|---|
| 实收登记/待审核/退回补正 | 0 | 0 | 留实收及审核记录，数量单列，不能补货/销售 |
| 审核通过 | 0 | +q | 一次入库流水；重复通过不再入账 |
| 在仓暂存无移动 | 0 | 0 | 不重复入库 |
| 补货上架 | +q | −q | 同事件双向流水，T不变，W不足阻止 |
| 销售确认 | −q | 0 | 仅从在售，整单收款/出库/快照一起生效，来源不足拒绝 |
| 退货/所有换货交回品 | 0 | 0 | 原销售关联、损耗/去向记录；既不回库也不再扣既有库存 |
| 换货替换品 | −q | 0 | 在售不足拒绝，在仓有货不能直接抵扣 |
| 店内现有货报损 | 若来源在售则−q | 若来源在仓则−q | 指定来源扣一次，另一位置不变，后续处置不重扣 |
| 授权作废 | 原业务对应的逆向数量 | 原业务对应的逆向数量 | 依据原单生成反向流水并留原因；退换退款亦同步冲销，不仅改状态；不能负库存 |
| 查询/已记损耗的实际处置 | 0 | 0 | 不自动调账或下架，不设不可售桶 |

q为1–9999整数业务数量，0和超界拒绝且不写库（R-INPUT已关闭）。到货审核已通过后需修正的记账历史不覆盖，可依已定授权逆向处理；库存依赖适用§7.5 D1及§10.2 D2，既有授权/售后关联保留。

### 7.2 日期事实、临期和批次

已撤销：商品日期、临期/过期、批次及过期销售拦截从P1和P2完全删除；不保留扩展点。编号只作历史追踪，不是功能或验收要求。 旧规则和原优先级仅留在v0.4备份。收货、补货、销售、退换、损耗不录入或选择商品日期/批次，库存按商品及位置汇总；无相关主键、外键或前置校验。业务经办时间、促销有效期及30天售后期限不属于此次撤销范围。

### 7.3 促销与金额统一口径

沿用优惠前行金额的既有规则：单价×数量保留4位中间值、行金额两位HALF_UP；订单汇总和候选比较均用整数分。先计算每个单一活动候选的整单优惠/应付，选最低应付；同价沿用显式优先级及活动ID决胜，不叠加。

活动有效期、折扣1–99%、满减金额边界及零价赠品规则不变；满减门槛只以适用行优惠前总额判断，合计0不触发正门槛活动，不除零。

选定整单优惠D分后，仅向本次活动适用销售行分摊。权重w为该行优惠前小计（整数分），W为适用行权重和。D>0时W必须>0。各行先分得整数商 floor(D×w/W)，剩余尾分按精确整数余数降序逐行各加1分；余数相同按不可变SALE_LINE.line_id升序。非适用行优惠0。无通用多轮封顶重算、重归一化或备用均分算法。

确认前校验每行0≤优惠≤其适用优惠前金额、实付=原额−优惠≥0、Σ行优惠=D、Σ行实付=整单应付；任一不变量失败拒绝整次计算，不生成部分销售记录。保存商品名、单价、促销及适用依据、优惠前金额、分摊优惠、实付和稳定销售行ID。上述规则替代旧促销末行承接尾差规则；售后HALF_UP规则不变。授权与历史见§17 CR07-02。

### 7.4 退货、退款分摊、换货

每条原销售行独立维护售后核销台账。设原购买数量Q、原行实付P；有效已退数量Qr/金额Mr、已换数量Qx/原商品抵扣金额Mx；剩余数量=Q−Qr−Qx，剩余金额=P−Mr−Mx。必须同时满足0≤Qr+Qx≤Q、0≤Mr+Mx≤P。换货先占用原销售行数量和实付金额，后续退货只能使用剩余额度；已生效核销不能被后续换货覆盖。部分退/换数量q必须为正且≤剩余数量；未结清时本次占用金额=min(HALF_UP(P×q÷Q,2),剩余金额)，最后一次结清剩余数量时占用全部剩余金额。退款直接使用原销售行保存的实付，不跨行重新分摊退款预算、不按原价或当前活动重算。换货占用的是原商品抵扣额度，不是新品售价或实际补退差；同款同数量质量换零补差也必须核销原数量及对应实付额度。每次核销记录原销售行、来源退/换单及明细、数量、金额、类型、经办人、时间、幂等标识及状态；同一请求重复提交不再次占用。退款、核销及替换品在售扣减按既有原子/防重规则同步，失败不留下部分生效。合法授权冲销以关联反向记录释放原数量/金额，保留原记录及原因，不物理删除、不重复释放。

既有30天本地日历期限、质量问题店长例外、店员日常独立办理、开封/质量换货资格继续有效。新品现价−本次原商品抵扣额度为换货补退差，正补负退零换；同款同数量质量换货零差，但仍占用原销售行双额度。替换商品只从在售扣，所有顾客交回品不回库、记录损耗或去向；这些记录不得再扣现有库存。



本轮新增独立业务规则（CR07-04）：同一张售后单提交时，先计算全部换货核销，再计算退款，与界面录入顺序无关；历史已确认占额不重算。资格opened、quality_problem逐REDEMPTION记录，不再放单头。允许同单不同资格、不同换货类型；头部既有超期例外授权/原因仅保留审计归属，不替代每条资格事实。

按原销售行分别计算，沿用本节既有P×q/Q、HALF_UP及剩余额度公式。当前提交内同类别拆分明细按稳定redemption_id升序处理；不能用标价、采购价或现价。只有当前提交的明细合计恰好结清该原行当时全部剩余数量时，当前提交内按上述次序最后结清的明细承接剩余分值。非结清明细用min(HALF_UP(P×q/Q,2),当时剩余金额)。未来售后不得回写当前已确认金额。

exchange_kind移至REPLACEMENT。特殊同款同数量质量零差额换货通过REPLACEMENT.quality_redemption_id显式关联同单换货CONSUME核销；该引用唯一，必须校验quality_problem=true、原商品与替换商品条码相同、数量相同、补退差额0。普通替换明细该引用为空。替换品只扣在售，交回品不回库；核销实付额度、替换品金额及实际补退差分别记录，特殊配对不得使其他普通换货免差。见ERD §5及CR07-01/03/04。

### 7.5 D1 库存冲销依赖范围

依据：CR07-06；批准状态唯一见§17.1。只把**同一商品、同一库存位置、commit_ordinal大于被冲销原业务流水的有效负向流水**判为后续库存依赖。位置W=在仓、S=在售。同一提交序号内流水不互为后续依赖；时间、ID、单据版本和文件排列不替代提交序号。无批次条件下保守阻断，不推断实际耗用了哪笔收货，不用商品总余额/净余额代替依赖检查。

本节的“有效负向流水”指未被完整授权冲销的负向流水；原流水与反向流水逐项配对后净额为0的，视为已完整冲销，不构成依赖。

| 对旧收货W+q的后续动作 | 依赖判断 |
|---|---|
| 同码新增收货W+q | 本身不阻断，也不清除另一笔有效负向依赖 |
| 补货W−q/S+q、在仓报损W−q | 同商品W位置后提交的有效负向腿直接阻断 |
| 销售S−q、换出S−q、在售报损S−q | 不直接阻断W收货；此前若有有效补货W−，由该补货阻断 |
| 顾客退货/换回品 | 不回库、无库存流水，不构成库存依赖；原销售售后关联约束仍保留 |
| 同一commit_ordinal内流水 | 同一原子业务，不构成“后提交”依赖 |

其他库存来源/位置同样逐商品、位置检查后提交有效负向流水，不扩大到所有同码事件。后续业务仅在获授权整单冲销、原流水与反向流水逐商品/位置/数量成对匹配且净额0、并且自身无未冲销售后/换货/部分退货时，才能完整排除；排除原流水及其配对反向流水整组，不只排除反向。部分退货、部分换货、仅退款不构成原销售完整冲销。

冲销对象始终为整张原业务单。逐行检查原单全部商品与位置；任一行依赖未解除即整单拒绝，任何行库存/状态/款项/核销都不部分生效，不生成部分反向流水。其他商品不影响判断仅指原单以外商品。冲销后库存非负是额外安全校验；既有授权、原销售售后关联、幂等与审计约束继续适用。

## 9 数据约束和核心概念

以下为P1逻辑数据约束，不是已实现类或数据库表。库存仅按商品＋位置，售后按原销售行核销；不要求数据库，P1仍用Java集合/File I/O。

| 概念 | 必要语义和关联 |
|---|---|
| 操作者/角色 | 具体经办标识、管理员/店长/店员身份；技术权限与日常审核策略区分；本地预置账号、用户名/哈希密码登录，无网络认证 |
| 商品 | 有效唯一条形码为主键（保留条码原文本语义，不以菜单序号代替），品牌＋商品名、固定包装计量单位、售价；无条码等不假造备用键；启停状态不等于位置 |
| 收货/明细/审核 | 实际到货、商品条码、整数数量、经办时间、审核结果/意见；待审数量不入余额；通过事件幂等标识可防重；补正与退供区分 |
| 位置流水/余额 | 商品＋在售/在仓；有符号整数、来源单/行/事件、经办/时间；期初来源；缓存可由流水重建；补货两方向归同一次转移 |
| 销售/明细 | 稳定销售/行ID，商品条码关联，名称、单价、原数量、促销、分摊折扣、原行实付快照；行原额−折扣=实付，实付合计=订单应付；原单快照不可被调价修改 |
| 促销/候选 | 折扣/满减、适用品、参数、活动ID和显式优先级信息；每候选一活动，比较同一订单；非法参数不保存；同价/活动日期按已关闭R-PROMO |
| 退货/换货 | 售后单及核销明细，明细必须关联原销售行；含退/换类型、数量、原商品核销金额、原行剩余额度、经办/时间、幂等键/状态；替换商品及新价/补退差单独记录，不与原商品抵扣金额混用 |
| 损耗/处置 | 来源店内报损/顾客交回，商品及数量、原位置（仅店内）、经办/时间/原因、实际暂存/处理；历史/待处置记录而非库存桶 |
| 作废/冲销 | 原单关联、原因、授权店长/管理员、逆向流水/退款反向记录；原单留存；不能仅改状态或重扣处置数量 |
| 附件/快照 | 本地副本、相对路径、哈希、所属收货单；JSON根含schemaVersion；启动与恢复校验来源关系、位置整数非负和原实付完整性 |

金额字段及舍入阶段统一执行§7.3，退款按§7.4；M-ROUND/R-REFUND均已关闭。状态分别表达收货审核、销售已收款、退换完成、损耗处置、作废，不把在售当可销售状态，也不将“退回补充／修正”当供应商退货。

生效单不可物理删除，草稿可删；历史快照不被商品调价覆盖；作废保留原关联并反向处理。通用关联校验/schemaVersion/附件哈希是需求，具体Java类/包/序列化DTO在后续设计完成，不把设计选择都变成重复用户问题。输入边界按R-INPUT、权限按§5、依赖冲销按R-VOID，均已由U4确认。

### 10.2 D2 快照内单调提交序号

依据：CR07-07，与D1成套；批准状态唯一见§17.1。P1继续集合/UTF-8 JSON单快照，临时文件＋原子替换＋上一版备份；无数据库、COMMIT业务实体、独立计数文件或排序模块，不新增无需求的commit_index。

| 数据 | 逻辑类型/必填 | 约束/用途 |
|---|---|---|
| 快照根last_commit_ordinal | Integer；必填 | 非负，初始空快照为0；存储元数据，不是业务实体；包括无库存流水的成功提交 |
| STOCK_ENTRY.commit_ordinal | Integer；必填 | 正整数、≤该快照last_commit_ordinal；同一次成功提交的全部库存流水相同，不设单条UK；不同成功提交序号递增；用于D1先后判断 |

启动时在DATA_ROOT下取得本地锁文件或操作系统文件写锁；锁失败只读或拒绝写操作，禁止第二进程并发写入。每次业务提交开始，在单写者锁保护下读last，候选值last+1只存在于该次内存工作副本。把候选last、业务记录及全部流水放在**同一个新JSON快照**内，只有原子替换成功后才对外生效并发布内存结果。无库存流水的成功业务提交也推进last，不能只按库存事件数计数。

校验、序列化、写临时文件或原子替换任一步失败，持久化last不变、候选不生效、记录和流水不可见，旧快照完整可启动；重试可重用未提交候选。临时文件不是已提交数据，不加载为业务快照。替换成功但响应前崩溃，重启以新快照为准，既有请求幂等键保证重试不重复记账。

启动/恢复读取last并扫描全部流水commit_ordinal；无流水时最大值按0处理。若last<max或类型/正值约束不符，快照不一致，阻断写入并提示恢复/人工核对；last≥max合法，大于可因无库存流水业务产生。下一次从last+1开始。只恢复完整快照及关联附件，不能混拼另一来源计数/流水/附件；恢复后重做关联、金额、库存、双额度、附件存在/引用/哈希和序号完整性校验，缺失或不一致阻断写入并提示处理。不以created_at、流水ID、单据版本、文件排列证明提交先后。

见AC-85；Ready仅表示规范具备预期，实际结果须获准实现后记录。DATA_ROOT默认定位、备份子布局和一般附件错误语义仍引用§10.1，D2不替它们定案。
